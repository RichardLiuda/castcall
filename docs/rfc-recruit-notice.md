# RFC：招募须知 · 招募版一图流 · 候补

**状态**：提案，未实现（评审用）
**来源**：一张真实的团片招募帖（11.28 广州磨碟沙 学园孤岛团片，微信群竖图）
**影响范围**：`site.json` 新增一个顶层块；`poster` 新增一个变体；候补阶段动报名状态机

---

## 1. 问题

团片招募帖的信息密度很高，但它整段是「图 + 文字」：发在微信群里，招满以后就废了，谁也不知道还缺不缺人。

castcall 能替掉其中「谁在、谁缺、怎么报名」，但**替不掉帖子里的规则部分**。现在能写规则的只有两处：

| 现有位置 | 实际能装什么 |
|---|---|
| `signup.note` | 报名表底部的一行小字，默认文案是「提交后等审核…」，最多一句话 |
| `group.note` | 团说明，显示在展开后的席位上方，是给已经点进来的人看的 |

而被那张帖子占掉一半篇幅的内容——卡什么、不收什么人、什么风格、退团怎么办——没有地方放。团长只能继续在群里补一段文字，或者做一张图。

## 2. 现状对照

以那张帖子逐条对照（✅ 已覆盖 / ⚠️ 部分 / ❌ 没有）：

| 帖子里的信息 | castcall |
|---|---|
| 11.28 / 广州磨碟沙 / 学园孤岛 | ✅ `event.date` `location` `title` + 倒计时 |
| 「缺」红标 /「有」橙标 | ✅ 空缺可点报名、已定阵容、缺人看板 |
| 立绘 + 真人试装并排 | ⚠️ 一个席位一张立绘；`photos` 是已定成员自己传的本人照，不是招募期的试装参考 |
| 卡 16+ / 卡 bmi / 卡妆造 / 卡表情管理 | ⚠️ 能收（`signup.fields` 有身高、年龄、性别、样片，还能加 6 道自定义题），但**没地方写「我们卡什么」** |
| 挡脸（黄色高亮，是核心卖点） | ❌ 无处可写 |
| 十一月出分镜、可以集思广益 | ❌ 无流程 / 日程 |
| 摄影是团员互勉、14:00–16:00 光好 | ⚠️ `kind: crew` 能表达「摄影是团员」，但「互勉」「这个时段」没位置 |
| 自然感、容貌焦虑/厚涂慎来 | ❌ 无风格取向 |
| 外景，确保自己受得了 | ❌ 无风险提示 |
| 退团找替补 | ❌ 报名只有 approve / reject / reopen，满了只能拒 |
| ❌ 低龄 精彩人 预算不足 瓜人 公主病 | ❌ 无不接受名单 |
| 团里妹子都很好、卡的多是为了好好相处 | ❌ 无氛围说明 |
| 联系方式 | ✅ `event.contact` |

结论：**缺的是「叙事空间」，不是字段**。门槛本身大多能用现有 `fields` 收到，真正没有的是「把规则明明白白写在报名按钮上方」的那块地方。

## 3. 目标与非目标

**目标**

1. 团长能在一处写下「要求 / 不接受 / 补充 / 风险」，并且这条信息在**单团页、报名表、一图流**三处自动复用。
2. 一键出一张能直接发群的招募图，替掉手工拼版。
3. （第二阶段）席位满了以后还能报名，进候补队列，有人退团时能接上。

**非目标**

- 不做报名者互评 / 互审。涉及公开他人信息，隐私成本和审核成本都不对等。
- 不做「自动按门槛筛人」。`fields` 的 `min`/`max` 是防乱填的输入校验，不是准入判断；自动拒人会把「有话好商量」的余地做没。
- 不改名册结构，不动立绘 / 照片那套。
- 不做多语言。

## 4. 数据模型

`site.json` 新增顶层块 `notice`，与 `signup` 平级：

```jsonc
"notice": {
  "enabled": true,
  "lead": "自然感团片，不修厚涂",            // 一句话定调，字号大于正文
  "items": [
    { "kind": "must", "text": "挡脸出图" },
    { "kind": "must", "text": "16+ / 妆造 / 表情管理在线" },
    { "kind": "warn", "text": "外景，确保自己受得了" },
    { "kind": "info", "text": "十一月出分镜，可以一起改" },
    { "kind": "deny", "text": "低龄、精彩人、预算不足、瓜人、公主病" }
  ]
}
```

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `enabled` | bool | 默认 `false` | 关掉时页面和现在完全一致 |
| `lead` | string | ≤ 40 字 | 可空；空了就不渲染那一行 |
| `items` | array | ≤ 12 条 | 超出部分服务端截断，不报错 |
| `items[].kind` | enum | `must` / `deny` / `warn` / `info` | 只有这四个值，其他值丢弃这一条 |
| `items[].text` | string | ≤ 80 字 | 前端按 80 字截断；渲染必须走 `esc()` |

设计约束：

- **四种 kind 就是四个视觉层级**，不再增加。加第五种会让团长不知道该选哪个，也让海报放不下。
- `lead` 和 `items` 分开，是因为前者是「调性」（一句话让人决定要不要继续看），后者是可检查的条目。
- 不做富文本。见到 `<` `>` `&` 一律转义，这个块会原样出现在公开页面上。

## 5. 展示规范

### 5.1 单团页（`soloHTML()`）

位置：「招募中」标题上方，`gmeta()` 之后。

```
┌─────────────────────────────┐
│ CAST CALL · 9 个角色         │
│ Kanon                        │
│ 3 已定   6 招募中             │
├─────────────────────────────┤
│ 自然感团片，不修厚涂          │  ← lead，16–18px，加粗
│ ▎挡脸出图                    │  ← must，左侧 3px 竖条
│ ▎16+ / 妆造 / 表情管理在线    │
│ ▎外景，确保自己受得了         │  ← warn，竖条换色
│               查看全部 5 条 ▾ │  ← 默认只显示前 3 条
├─────────────────────────────┤
│ 招募中 6                     │
```

- 默认显示前 3 条（优先 `must`，其次 `warn`），其余折叠；
- 展开后全部铺开，按钮文案变「收起 ▴」，状态存 `sessionStorage`，同一次会话内不再折叠；
- 没有 `items` 但 `enabled` 为真时不渲染区块，避免出现空壳；
- 移动端（< 640px）默认折叠成 2 条。

### 5.2 报名表（`openSignup()`）

位置：提交按钮上方，现在 `.signup-fine` 的地方。

- 只取 `must` 和 `deny` 两类，最多 4 条，超出显示「还有 N 条，见页面须知」；
- `deny` 前缀加 `✕`，`must` 前缀加 `·`；
- `signup.note` 保留，排在须知**下面**一行，继续承担「提交后等审核」这类流程话；
- 这块是唯一的「同意条款」位置，不能折叠。

理由：报名表是全屏弹层，用户已经决定要报了，这里要压的是「你不符合就别浪费彼此时间」的信息，所以只留硬条件。

### 5.3 缺人看板（`.cast-note`）

位置：看板底部的联系方式上方，压成一行：

```
16+ · 妆造 · 挡脸 · ✕ 公主病
```

取 `must` 和 `deny` 各最多 2 条，用 `·` 连接，超出加 `…`。字号沿用 `.cast-note`，不做强调。

### 5.4 一图流（见第 6 节）

海报里用同一份数据的摘要版，不展开。

## 6. 招募版一图流

现有变体：`master`（竖版阵容）、`wide`（宽版）、`social`（单团卡片 1080×1350）。
新增 `recruit`：**1080 × 1920**，微信 / 小红书竖屏整图，目标是「发群里就能被看懂，并且想点链接」。

区块顺序（自上而下）：

| # | 区块 | 内容 | 说明 |
|---|---|---|---|
| 1 | 标题条 | `title` + `date` + `location` | 复用 `title()`，大标题压在封面或主题色上 |
| 2 | 缺口行 | `缺 胡桃 · 缺 XX · 已定 5` | 整张图最该被看到的一行，字号仅次于标题 |
| 3 | 角色卡 | 只画空缺席位，2 列，最多 6 个 | 复用 `section()` / `card()`，超出显示「还有 N 个空缺」 |
| 4 | 须知摘要 | `must` 一行、`deny` 一行 | 超出省略号，完整内容在网页上 |
| 5 | 页脚 | 二维码 + `event.contact` | 二维码位置先留白框，第二阶段接短链生成 |

实现方式：沿用 `variants` 参数，`python3 poster/build.py recruit`，后台「生成一图流」下拉里多一项。不新增接口。

与 `social` 的关系：`social` 已经是 1080×1350，`recruit` 与它的差异集中在「缺口行 + 须知摘要 + 页脚二维码」，角色卡部分可直接复用。

## 7. 候补队列（第二阶段）

现在有个绕不开的耦合：**席位满了，「报名 →」按钮就消失**——入口条件是 `castKind(g.name, m) === 'vacant'`（`soloHTML()` 的 `seat()` 与 `openSheet()` 都用了）。要支持候补，就得让满员席位仍然可点。

状态机：

```
提交 → pending ──approve──→ approved
              ├─reject───→ rejected
              └─(席位已满)→ waitlist ──有人 reopen──→ pending（等团长处理）
```

规则：

1. 席位已有人时提交 → 直接落 `waitlist`，按钮文案改为「满员 · 进候补」，提交成功提示「已进候补，排在第 N 位」；
2. 团长 `reopen` 某席位 → 后台弹提示「泽渡真琴空出来了，候补 2 人」，列出候补者，团长手动选一个 `approve`；
3. 审核面板加「候补」筛选页签，按报名时间正序；
4. 候补不占用席位，不进 Notion 名册同步，只进报名库；
5. `signup.closesAt` 之后候补也一并关闭。

接口变化：

| 接口 | 变化 |
|---|---|
| `POST /api/signups` | 席位已有人时返回 `{"ok":true,"status":"waitlist","position":2}`，不再返回 409 |
| `GET /api/admin/signups` | 多返回 `waitlist` 状态；`counts` 里 `signups.waitlist` |
| `POST /api/admin/signups/<id>` | `action` 增加 `waitlist`（手动把一条转成候补） |

## 8. 兼容与迁移

- 老 `site.json` 没有 `notice`：`DEFAULTS` 补默认值 `{"enabled": false, ...}`，页面渲染结果与现在**逐像素一致**，`tests/e2e_browser.py` 的既有断言不受影响。
- `config.merge()` 是深合并，`items` 是数组会被整体替换，符合预期（不会出现「只改了一条，其余消失」以外的意外——文档里要写明：数组是整体替换）。
- `poster` 的 `variants` 是显式列表，不写 `recruit` 就不会生成，不影响已有实例。
- 候补阶段：`signups.status` 是文本列，加 `waitlist` 不需要迁移；旧记录不受影响。

## 10. 验收标准

**notice（第一阶段）**

1. `site.json` 不写 `notice`：单团页、报名表、一图流的 DOM 与改动前一致（用 `tests/e2e_browser.py` 的既有断言回归）。
2. 写 5 条：单团页默认显示 3 条 + 「查看全部 5 条」，展开后 5 条全在，再刷新回到折叠。
3. 报名表只出现 `must` / `deny`，最多 4 条；`info` 不出现。
4. 缺人看板底部那行不超过 2 条 `must` + 2 条 `deny`。
5. 文本里的 `<script>` 原样显示为文字（`esc()` 生效）。
6. 390px 宽下无横向溢出；须知块不与「招募中」标题重叠。
7. 后台改完保存，刷新页面立即生效，不用重启服务。

**recruit 一图流**

8. `python3 poster/build.py recruit` 产出 1080×1920 的图片，缺口行、角色卡、须知摘要、页脚都在。
9. 没有空缺时不生成缺口行，改为「全员已定」。
10. 没装 Pillow / Playwright 时，后台返回 501 和安装指引（沿用现有 `poster_status` 提示）。

**候补（第二阶段）**

11. 席位已有人时仍能点报名，提交后提示「已进候补，排在第 N 位」。
12. 团长 `reopen` 后出现候补提示，`approve` 候补者后席位正常落座，其余候补位次前移。

## 11. 样例配置

用那张帖子直接转写（可直接粘进 `instance/site.json`）：

```json
"notice": {
  "enabled": true,
  "lead": "自然感团片 · 11.28 磨碟沙学园孤岛",
  "items": [
    {"kind": "must", "text": "挡脸出图"},
    {"kind": "must", "text": "16+，卡妆造、卡表情管理，可以互审"},
    {"kind": "warn", "text": "外景，确保自己受得了；摄影是团员互勉"},
    {"kind": "info", "text": "视频照片都拍，十一月出分镜，可以一起改；退团请自己找替补"},
    {"kind": "deny", "text": "低龄、精彩人、预算不足、瓜人、公主病"}
  ]
}
```

## 12. 备选方案与取舍

| 方案 | 为什么没选 |
|---|---|
| 把须知塞进 `group.note` | 那段是「团说明」，显示在展开后的席位上方，只有点进来的人看得到；且它是纯文本，做不了 must / deny 的分级 |
| 给每个席位加 `note` 字段写门槛 | 门槛是活动级的，不是角色级的；九个角色填九遍会疯 |
| 用 `signup.fields` 的 `min/max` 做自动筛人 | 那些是输入校验（防乱填 999 岁），不是准入判断。自动拒人会误伤，也和「有话好商量」的调性冲突 |
| 候补先做「名额上限」 | 团片是按角色招的，不是按人数招的；「这个角色满了」才是真实语义，人数上限解决不了 |
| 招募图直接生成长图（把须知全文排进去） | 群里刷屏的长图就是现在这个样子，学它就是退步。图只负责「让人想点进来」 |

## 13. 阶段建议

| 阶段 | 内容 | 依赖 |
|---|---|---|
| P1 | `notice` 数据 + 三处展示 + 后台编辑 | 无 |
| P2 | `recruit` 一图流变体 | P1（读同一份 `notice`） |
| P3 | 候补队列 | 无（可与 P2 并行） |

P1 完成后，`docs/config.md` 补字段表，`skills/castcall-setup/SKILL.md` 里加一句「建站第 4 步可以顺手写招募须知」，这样 AI 助手建站时会主动问团长要不要填。
